# 贴合项目的代码

把“AI 味”转成可以评审的工程问题：哪段代码增加理解成本、遮蔽错误或违背本地约定？先读相关实现、调用者、测试和项目规范。用户只要求审阅时给建议；要求修改时，在授权范围内做有依据的最小改动。

## 检查与修改

- 沿用现有命名、错误处理、配置和依赖方式。引入新结构前查找可复用实现。
- 重复代码按是否承担同一职责判断。没有现实调用需求的 factory、manager、wrapper、配置层或兼容分支可作为审阅线索；它们存在本身不构成删除依据。
- 抽象要有当前需求或明确契约。不要为了整齐重写整个模块，也不要为了减少行数破坏职责边界。
- 注释解释原因、契约和约束。删除逐行翻译代码、过时标题和未经验证的“robust/production-ready”。保留必要的 API 文档、许可、算法出处和业务理由。
- 检查无声吞异常、伪造成功返回、未用变量、调试输出、硬编码路径与默认参数。这些属于功能或维护问题，修复时要说明可观察行为。
- 保留 public API、类型契约、错误语义和边界条件，除非任务明确要求变更。不要通过给程序添加随机性、随意命名或删除类型来制造“手写感”。
- 对任务相关的失败路径和边界选择验证方式。测试应检验行为与回归风险，避免只断言新函数存在、重复实现本身或以空 mock 宣称集成成功。
- 报告实际执行的检查与局限。没有运行环境时说明；不要用“应该通过”冒充已运行结果。

交付说明问题、对应改动、行为影响及验证证据。单纯格式偏好应服从项目规范，不扩展为架构重构。

## 复核

改动是否更容易理解？是否删掉仍有作用的契约或校验？现有调用者是否仍符合预期？错误还能被观察到吗？新增层次是否有当前用途？
