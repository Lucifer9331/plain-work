# 可用的项目文档

明确读者是谁、来这里要完成什么。已有仓库时，先查看相关文件、命令入口、配置和验证记录，再决定能写哪些事实。任务只给一段文字时，在该段范围内修改，标明需要作者核实的技术事实。

## 写作与改写

- 开头交代项目做什么、当前可用到哪一步。使用具体输入、输出和适用任务，删除无依据的“强大、完整、无缝、生产级”。
- 按读者的实际操作顺序组织安装、最短运行路径、输入输出、限制。章节随项目需要安排，避免填充空的路线图和贡献口号。
- 命令、路径、版本、环境变量、输出样例都需要来源。区分“代码里存在”“已运行验证”“尚未验证”。未执行的命令不得写成已测试。
- 原样保护代码块、命令、链接目标、标识符和版本。发现错误时单独说明依据再修正，不能作为文字润色默默更换。
- 对“不是 X，而是 Y”检查比较是否帮助读者选择。直接描述功能通常足够；兼容性、支持范围及容易混淆的概念需要清楚区分。
- 每节解决一个实际问题。合并重复背景，删除标题后的标题释义、密集粗体和重复总结。表格用于真实可比较字段。
- 限制写到触发条件和后果。不要删除“尚未完成”“不支持”等信息来提升观感。
- 项目叙述使用项目自己的术语和现有风格，避免把解释工作过程的聊天残留写进面向用户的文档。

用户要求直接修改文件时，在授权范围内编辑；纯审阅先给建议。交付说明关键变更、核实过的事实和未核实项，避免宣称文档“全面完善”。

## 复核

读者能找到起点并完成最短任务吗？事实、路径和状态是否保真？每个能力声明是否有证据？必要限制是否保留？语气是否符合该项目？技术验证按变更风险选择，单纯删套话无需启动完整测试集。

例子见 [examples](references/examples.md)。科研指标与复现结论需要单独核对来源，不靠措辞修饰解决。
