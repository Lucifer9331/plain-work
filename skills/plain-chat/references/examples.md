# 对话中的改写判断

以下均为构造示例。

用户问“这个脚本怎么启动？”

- 冗余：“你真正需要的不是理解所有细节，而是掌握一个清晰、可靠的启动流程。”
- 有命令依据时：“在项目目录运行 `python app.py`。”
- 无依据时：查看入口文件和文档，再给命令；不要猜入口。

原句：“这不是效率问题，而是思维模式的问题。”

若没有证据支持这种归因，改为具体观察：“目前有三个步骤需要重复录入数据，可以先把它们合并。”仅在确有这些事实时使用。

用户说“这个错误说明服务器崩了吗？”

“不一定。401 通常表示认证失败，需要先检查凭据。”保留否定，因为它回答了用户的判断。

“别把 API 密钥写进日志。”保留约束和否定。安全说明、语义逻辑、真实纠错无需为风格让路。

用户说“我改了半天还是报错，很烦。”

“反复遇到同一个报错确实磨人。把最新错误贴出来，我们从第一处异常看。”比替用户诊断“你陷入了完美主义”更贴合当前证据。

英文套话：“Great question! Let's dive into this fascinating topic.”

直接给用户所需的解释。专业交流仍可以礼貌，支持性的语言应呼应具体情境。
